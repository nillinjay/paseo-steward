# Can a worker live inside a `bwrap` sandbox?

**Probe date:** 2026-10-21  
**Host:** `nil-kubutntu`, bubblewrap `0.9.0` (`/usr/bin/bwrap`, mode `0755`, not setuid)  
**Repository:** `paseo-steward` at base `658ae3beb4b8a3176aa04335c0f293d51ead74d8`  
**Runner:** `tools/bwrap-probe.sh` (`./tools/bwrap-probe.sh` exits `0`)

## The user-namespace question is already answered

The steward read the host value on 2026-10-21:

```text
unprivileged_userns_clone = 1
```

Unprivileged user namespaces are allowed, so the sandbox can be created. This leg did **not** run
`cat /proc/sys/...` and did not re-read that value. Everything below is a consequence of actually creating
the sandbox, not of that host setting alone.

## The shape under test

Every command below ran with this prefix (`$WT` is a throwaway directory under `/tmp`):

```bash
bwrap --ro-bind / / --bind "$WT" "$WT" --dev /dev --proc /proc --tmpfs /tmp/scratch \
      --unshare-pid --die-with-parent --chdir "$WT" -- <command>
```

Two mechanical details matter:

- `/tmp/scratch` must exist on the host before `bwrap` starts. `--ro-bind / /` makes `/tmp` read-only,
  so `bwrap` cannot create the mountpoint itself: `bwrap: Can't mkdir /tmp/scratch: Read-only file system`.
  The probe creates that one host directory under `/tmp`; the tmpfs hides its contents.
- Network is **not** unshared. The shape has no `--unshare-net`, so the sandbox inherits the host network.
  No network option was opened for any question below.

## 1. Does a git worktree still work inside?

The worktree was a fresh `git init -b main` repository under `/tmp`, bound read-write over itself.

```bash
$ bwrap --ro-bind / / --bind "$WT" "$WT" --dev /dev --proc /proc --tmpfs /tmp/scratch \
        --unshare-pid --die-with-parent --chdir "$WT" -- git status --short --branch
## main
exit=0
```

```bash
$ bwrap ... -- sh -c 'printf "one\n" > probe.txt && git add probe.txt \
        && git -c user.name=Probe -c user.email=probe@example.test commit -m "bwrap probe commit"'
[main b9d1429] bwrap probe commit
 1 file changed, 1 insertion(+)
 create mode 100644 probe.txt
exit=0
```

```bash
$ bwrap ... -- git log -1 --oneline
b9d1429 bwrap probe commit
exit=0
```

The commit persisted in the bound worktree; `git status` saw a clean `main`.

**Verdict: yes — `git status`, `git commit` and `git log` all work inside the sandbox (exit `0`).**

## 2. Can a write escape?

A write to `/tmp/...` (outside the bound worktree) was attempted first:

```bash
$ bwrap ... -- sh -c "printf 'escape\n' > /tmp/bwrap-probe-outside-1949558"
sh: 1: cannot create /tmp/bwrap-probe-outside-1949558: Read-only file system
exit=2
PASS /tmp/bwrap-probe-outside-1949558 does not exist on the host
```

A write to the sandbox-private tmpfs was then attempted:

```bash
$ bwrap ... -- sh -c "printf 'scratch\n' > /tmp/scratch/probe.txt && cat /tmp/scratch/probe.txt"
scratch
exit=0
PASS /tmp/scratch is a private tmpfs; nothing leaked to /tmp/scratch on the host
```

The exact denial is `Read-only file system` (`EROFS`), not a permission check that could be widened by
policy. The only writable location in this shape is the bound worktree and `/tmp/scratch`.

**Verdict: no — a write outside the bound worktree fails with `Read-only file system`, while `/tmp/scratch`
accepts writes.**

## 3. Is the Paseo CLI usable inside?

Binary: `/home/dev/code/paseo/packages/cli/bin/paseo` (a Node ESM entry point).

```bash
$ bwrap ... -- /home/dev/code/paseo/packages/cli/bin/paseo status --json
{
  "home": "/home/dev/code/paseo/.dev/paseo-home",
  "pid": null,
  "startedAt": null,
  "listen": null,
  "hostname": null,
  "configuredListen": "100.65.84.38:6768",
  "localDaemon": "stopped",
  "desktopManaged": false,
  "logPath": "/home/dev/code/paseo/.dev/paseo-home/daemon.log",
  "connectedDaemon": "not_probed"
}
exit=0
```

The binary runs and emits valid JSON, but inside the required PID namespace it cannot see the host daemon
process, so it reports `localDaemon: stopped` and never probes the endpoint. The control (same shape **minus**
`--unshare-pid`) shows the cause:

```bash
$ bwrap --ro-bind / / --bind "$WT" "$WT" --dev /dev --proc /proc --tmpfs /tmp/scratch \
        --die-with-parent --chdir "$WT" -- /home/dev/code/paseo/packages/cli/bin/paseo status --json
{
  "pid": 24657,
  ...
  "localDaemon": "running",
  "connectedDaemon": "reachable",
  ...
}
exit=0
```

A one-off probe with `--host 100.65.84.38:6768` reached `"connectedDaemon": "reachable"` but returned
`DAEMON_REQUEST_TIMEOUT` (exit `1`), the same timeout the CLI also reports outside the sandbox. That says the
transport is reachable, not that a request completes reliably.

No networking was opened: `--unshare-net` is absent from the shape, so the sandbox inherited the host
network namespace. The limitation here is DNS-free local-process discovery under `--unshare-pid`, not a
missing network grant.

**Verdict: partially — the CLI and its JSON output work, but under `--unshare-pid` it reports the local
daemon as `stopped`; seeing the daemon requires dropping that namespace or naming a `--host` endpoint.**

## 4. Does the toolchain survive?

Run against this repository's `tsconfig.json` (`npx tsc --noEmit`), with the repository visible read-only
through `--ro-bind / /`:

```bash
$ bwrap ... -- sh -c 'cd <repository> && node --version && npx tsc --noEmit && echo TSC_OK'
v22.23.3
TSC_OK
exit=0
```

`tsc --noEmit` completed in about 1.5 seconds and wrote nothing, so the read-only root is not a problem for
type checking.

**Verdict: yes — Node `v22.23.3` runs and `npx tsc --noEmit` exits `0` inside the sandbox.**

## What this does NOT prove

- **The daemon launch path.** Only the CLI was run. Whether the daemon itself can start, write `paseo.pid`,
  bind `100.65.84.38:6768`, and survive under this shape was not tested.
- **The plugin provider `command` override.** No provider command or agent launch was exercised. A provider
  may resolve binaries, write caches, or expect a writable `HOME`; this probe only showed that a read-only
  root is enough for `tsc --noEmit`.
- **Performance.** One typecheck and three git commands say nothing about agent throughput, cold caches,
  large repositories, or I/O overhead.
- **Steering and MCP traffic.** No `paseo send`, steer, or MCP request was attempted. The PID-namespace
  finding predicts trouble for local-daemon discovery; it does not describe remote steering, message
  delivery, or MCP authorization.
- **Write containment beyond this shape.** There is no `--unshare-net`, no seccomp filter, no cgroup limit
  and no user-namespace UID remapping in the tested shape. The escape result applies to the `--ro-bind / /`
  layout shown above, not to every possible bubblewrap configuration.
- **Portability.** The `/proc` line is host-specific. A different host may disallow unprivileged user
  namespaces even though this one allows them.

A documented unknown is cheaper than an assumption.
